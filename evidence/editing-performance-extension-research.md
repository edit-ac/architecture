# Editing performance and first-party extension research

Research date: 2026-10-12. Scope: deepen existing editing, extension and qualification contracts. This document proposes acceptance refinements for existing owners; it adds no roadmap, implementation, benchmark result or support claim.

## Existing foundation and evidence limits

The [extension library](../specs/extension-library.md) already requires validated registration, frozen session registries, prepared commands, shared history, unknown-data retention, scoped subscriptions and presenter cancellation/disposal. The [regression suite](../specs/editing-regression-suite.md) already owns atomic edits, semantic selection, bounded normalization, nested event ownership and independent oracles. The [rich-content contract](../specs/rich-content-extensions.md) already separates derived highlighting from authoritative content, bounds worker queues, targets affected tables, and requires a single final block-move commit. These boundaries should be strengthened in place.

The [verification targets](../specs/verification.md) are provisional and require production artifacts, raw samples and pinned device profiles. Existing local receipts must not be promoted into end-to-end performance evidence: [ENG-1.21](engine-editor-profile/receipt.json) explicitly disclaims release/performance claims; [ENG-1.22](engine-retained-presentation-profile/receipt.json) records fixture-only functional qualification and `production_support: false`. Their recorded functional counts concern those snapshots, not the current complete editor. This research did not execute runtime tests, inspect all implementation paths, run benchmarks or use paid inference. It does not establish that any reported gap is a current implementation defect.

## Primary-source findings

The following mutable primary documentation was checked on the research date. These are design precedents, not dependencies or proof that edit.ac must copy another editor's implementation.

| Source | Verified behavior | Consequence for edit.ac |
|---|---|---|
| [ProseMirror editor props](https://prosemirror.net/docs/ref/#view.EditorProps) and [property lookup](https://prosemirror.net/docs/ref/#view.EditorView.someProp) | Event handlers and property resolution have explicit order and short-circuit behavior. | First-party features need reviewed precedence and one event owner; installation order cannot accidentally decide whether Enter accepts a menu, inserts a newline or edits a nested control. |
| [Tiptap extension priority](https://tiptap.dev/docs/editor/extensions/custom-extensions/create-new/extension#priority) | Priority affects plugin order and schema order. Its documented paste transforms compose in priority order. | Qualify supported preset ordering, conflicts and transformation pipelines. Do not assume each individually passing extension yields a passing combined editor. |
| [Lexical node transforms](https://lexical.dev/docs/concepts/transforms) | Transforms can share one reconciliation. Updates from update listeners add rendering work and can disturb history; transform preconditions matter for termination and order bias. | Assert bounded interacting rules, a stable result and attributable render/history counts; do not repair a completed action through a chain of observer-origin edits. |
| [Tiptap integration performance](https://tiptap.dev/docs/guides/performance) | Its React guidance identifies unnecessary editor rerenders and recommends isolating components from unrelated state updates. | Profile packed host consumers as well as the engine. Toolbar, inspector and application state must not repeatedly rebuild editor views or reset selection. |
| [Interaction to Next Paint](https://web.dev/articles/inp) | INP observes click/tap/key interactions; hover, zoom and scroll are not themselves observed interactions. | Retain input-to-visible measurements and add separate continuous-interaction traces. An INP result cannot qualify dragging, edge auto-scroll, touch selection or scrolling. |

## First-party presets and event ownership

Official first-party delivery should supply tested configurations with declared compatibility and deterministic precedence. It should not require application authors to discover safe ordering by trial and error. Extend existing descriptor/profile records rather than creating a second configuration system.

| Acceptance refinement | Existing implementation owner | Required evidence |
|---|---|---|
| Record preset identity/version, included descriptors/presenters, dependencies, conflicts and declared input/clipboard precedence. Reject duplicate namespaces, unsupported combinations and invalid options before attaching or mutating a document. | EXT-1.2, EXT-1.3; FIT-1.2 | A packed supported preset works without order-sensitive host glue; missing dependencies/conflicts yield an actionable bounded error and unchanged semantic state. |
| Normalize order only where the contract declares ordering irrelevant. Where order is meaningful, preserve reviewed precedence and test competing handlers. Do not demand arbitrary permutation equivalence. | EXT-1.3, EXT-1.5; RGS-1.7 | Deterministic collision cases for Enter, Tab, Escape, paste, drop, slash/reference triggers and keyboard shortcuts; precisely one accepted owner, or deliberate fall-through to native behavior. |
| Freeze the semantic registry per session. Presenter activation/deactivation may change presentation only under the existing lifecycle contract; disable/unavailable states preserve content and export fallback. | EXT-1.4, EXT-1.6, EXT-1.9; FIT-1.5 | Reopen the same document under baseline/disabled/enabled profiles. Unknown content survives. Late presenter results cannot revive a disabled feature, steal focus or change history. |
| Separate text-selection drag, block reorder, table-cell selection and nested-input drag ownership. A text drag must not start block reorder or cause native and custom handlers to insert twice. | RCH-1.17; EXT-1.6; RGS-1.7 | Selection inside code, tables, links and custom views; accepted/canceled drops; one final action with intended source/destination selection and history; no semantic commit from hover. Platform input evidence remains separately required. |
| Qualify directly interacting feature sets, not only each extension alone. | EXT-1.5, RCH-1.20; RGS-1.6, RGS-1.7 | Baseline, official preset and risk-driven pairs/triads: table + nested control + clipboard; code highlighting + composition + history; menu/reference + formatting + selected replacement; drag + remote edit + custom view. Record tested combinations and uncovered combinations explicitly. |

Do not enumerate the power set of all extensions. Existing profiles should name shipped presets and use interaction-based case selection. A failed unsupported host configuration must be distinguishable from a regression in an official preset. Schema/order changes, preset changes and new event handlers invalidate the relevant combined-profile evidence.

## Failure containment with honest limits

EXT-1.5, FIT-1.4 and RGS-1.6 already own failure/lifetime safety. Add injected presenter mount/update/dispose failures, failed lazy imports, provider rejection, canceled work, stale target completion and queue saturation to their existing fixtures. Test sibling features after the failure and type a sentinel into the outer editor to prove focus/input recovery. Committed user edits remain committed; reporting a failed callback must not replay the command or duplicate history/publication/persistence. Surface a safe fallback or bounded error rather than silently losing source.

First-party code still runs inside a shared process or JavaScript thread. Catching exceptions does not preempt a synchronous infinite loop or eliminate retained-memory faults. Do not claim a security/process sandbox from typed interfaces, timeouts or first-party ownership. Prevention consists of bounded pure work, qualified callback paths, measurable resource ownership and isolating suitable heavy derived services behind the already planned cancellable worker ports. Hard process isolation is a separate architectural decision only if a real requirement appears.

## End-to-end performance gates

FIT-1.8 and RCH-1.20 should extend existing profiles with the following acceptance fields. EXT-1.9/FIT-1.6 remain responsible for packed loading checks. No new numerical budget is proposed here; retain the existing total budgets and make any new limit a reviewed profile decision before measurement.

1. **Measure the user action through presentation.** Attribute input queue delay, target/selection capture, command preparation, commit, relevant persistence handoff, subscription work, rendering, style/layout and the first correct visible result. Measure durability separately when the user-visible edit precedes its durable receipt. A DOM mutation or engine microbenchmark alone is not the visible-update measurement. Verify timing instrumentation's actual paint/OS-presentation boundary and record any proxy limitation.
2. **Measure continuous interaction separately.** Record frame intervals, missed frames, geometry reads/layout work and destination/caret correctness during text drag, block drag, edge auto-scroll, touch selection and scroll. Pin refresh rate; retain the existing controlled 60 Hz budget and do not infer high-refresh support from it. Include selection feedback and menu positioning, not only final drop latency.
3. **Exercise mixed work on the same supported fixture.** Compare minimal, extensions installed but disabled, and the official enabled preset with identical content and capability requirements. Type/select/undo while highlighting, asset completion, resolver completion, remote bursts and journal work use deterministic prepared schedules. Keep task/long supported fixtures distinct from diagnostic large/aged stress runs.
4. **Assert bounded hot-path work.** Record touched blocks/cells, subscribers called, token spans applied, view replacements, DOM writes, geometry reads, queue depth, retained cache bytes and live resources. An unrelated edit must not serialize/reparse the whole document, scan all tables, restart every grammar or invoke every presenter. Necessary large changes use their declared bounded batch/yield/fallback policy and retain one intentional semantic/history action.
5. **Include host integration and lifecycle.** Profile the packed SDK consumer with toolbar/inspector state, one/ten active editors and the existing static-preview fixture. Include hidden/resumed editors, document switches, canceled activation and repeated mount/dispose cycles. Record memory plateau, workers, observers/listeners, object URLs and queued callbacks after bounded settling. Background work must not refocus an editor or keep an unused render loop alive.
6. **Preserve functionality while improving cost.** Rendering/viewport optimizations must retain model ownership, composed text, accessible navigation, native selection and search/clipboard behavior across offscreen content. Qualify these with feature/device owners before treating fewer DOM nodes as a passed optimization. Do not add a new virtualization framework merely to improve a microbenchmark.

Report p50/p95/p99 and raw samples, fixture/preset/implementation hashes, exact browser/device/OS/refresh profile and failed/skipped counts. Report cold/lazy activation separately from warm editing, and transfer/copy/apply costs separately from worker CPU. Record peak and steady memory. A first-party preset has its own qualified envelope; a fast minimal profile does not establish its latency.

## Adoption within the existing plan

Fold these refinements into the existing extension-library, rich-content, ecosystem-maintainability, verification and regression-suite specs and their named parent tasks. Retain the task count and prerequisite graph. RGS owns shared instrumentation/oracles, EXT owns preset/descriptor conformance, RCH owns rich feature behavior, FIT consumes qualified per-feature performance/compatibility evidence, and existing native/mobile extension tracks provide actual platform results. None should manufacture another owner's passing receipt.

The strongest architecture claim supported now is that the planned boundaries can express these requirements without adding another state owner, plugin runtime or test framework. Excellent behavior and performance still require executed evidence across the advertised envelope. Neither documentation completeness nor bounded generative testing can prove every possible editor action works perfectly, and no inspected evidence supports a comparative “best ever” claim.
