# Mobile web editing platform research

Checked **2026-10-11**. This is source research and proposed qualification coverage, not evidence that edit.ac has implemented or passed these behaviors. No browser, physical device, simulator, benchmark, speech service or inference provider was exercised. Browser support data below was checked against MDN browser-compat-data commit [`3b28abed321540dcbe571c16174af543c4e02ac0`](https://github.com/mdn/browser-compat-data/tree/3b28abed321540dcbe571c16174af543c4e02ac0), dated 2026-10-09. Future qualification must record its own exact browser, OS, device and keyboard versions.

## Required outcomes and optional browser APIs

The recommended release contract requires usable editing in the declared iPhone/iPad Safari and Android Chrome/Firefox support envelope. Text entry, selection, replacement, undo, paste, access to commands and caret visibility remain required when an optional API is absent. An unavailable OS input mode can be recorded as unavailable for that configuration; it must not excuse failure of ordinary typing or turn the whole mobile web surface into an optional feature.

| Mechanism | Source-supported status at the check date | Contract consequence |
|---|---|---|
| `contenteditable`, `beforeinput`, `input`, composition and Selection/Range | Browser editing foundation; `beforeinput` is widely available, but real user modifications can omit it or be non-cancelable. | Keep a browser editing path with post-mutation reconciliation; receiving one API does not prove all input methods work. |
| `VisualViewport` | Compatibility data records Safari 13, Chrome 61 and Firefox Android 68 onward. | Use available geometry as an input to caret/overlay placement; preserve a functional scroll/focus fallback. |
| `svh`, `lvh`, `dvh` | Compatibility data records Safari 15.4, Chrome 108 and Firefox 101 onward. | Useful for browser-chrome layout; not sufficient proof that a virtual keyboard is avoided. |
| `interactive-widget` viewport metadata | Chrome Android supports its modes from 108. Firefox Android defaults to `resizes-visual` from 132. WebKit implementation has progressed, but a landed change is not a Safari release guarantee. | The host may opt in for a qualified target. Basic editing must survive the browser default and unsupported metadata. |
| `VirtualKeyboard` | MDN data: Chromium from 94; Safari and Firefox unsupported; experimental. | Progressive geometry/control integration, detected at runtime. Never require it to open a keyboard or keep text reachable. |
| `EditContext` | MDN data: Chromium from 121; Safari and Firefox unsupported; experimental. | An optional independently qualified input backend, with the baseline backend retained. |
| `Keyboard.getLayoutMap()` / `Keyboard.lock()` | MDN data: Chromium from 69 / 68; Safari and Firefox unsupported; experimental. | Optional shortcut-label/fullscreen enhancements. Ordinary commands and keyboard editing cannot depend on them. |

Sources: [beforeinput behavior](https://developer.mozilla.org/en-US/docs/Web/API/Element/beforeinput_event), pinned [VisualViewport data](https://github.com/mdn/browser-compat-data/blob/3b28abed321540dcbe571c16174af543c4e02ac0/api/VisualViewport.json), [viewport-unit data](https://github.com/mdn/browser-compat-data/blob/3b28abed321540dcbe571c16174af543c4e02ac0/css/types/length.json), [VirtualKeyboard data](https://github.com/mdn/browser-compat-data/blob/3b28abed321540dcbe571c16174af543c4e02ac0/api/VirtualKeyboard.json), [EditContext data](https://github.com/mdn/browser-compat-data/blob/3b28abed321540dcbe571c16174af543c4e02ac0/api/EditContext.json) and [Keyboard data](https://github.com/mdn/browser-compat-data/blob/3b28abed321540dcbe571c16174af543c4e02ac0/api/Keyboard.json). `chrome_android: mirror` in those data files inherits Chromium compatibility; it is not a successful mobile editor test.

## Input, correction and handwriting

Input Events Level 2 describes editing intent and target ranges, including non-cancelable `insertCompositionText`. It is a standards document, not proof of a particular browser/keyboard event sequence. MDN separately documents real-world missing/non-cancelable `beforeinput` for IMEs, corrections and autocomplete. Therefore qualify resulting content, selection and transaction boundaries; record event order for diagnosis without requiring all platforms to produce one trace. [Input Events Level 2](https://www.w3.org/TR/input-events-2/), [beforeinput caveats](https://developer.mozilla.org/en-US/docs/Web/API/Element/beforeinput_event).

WebKit's editing documentation explicitly treats spellcheck/autocorrect as range replacement: the affected range need not be the current collapsed caret. Recommended cases therefore replace existing words in the middle of a paragraph, accept/reject a suggestion, undo the replacement, and continue typing across a mark boundary. A handler that only appends `event.data` at the caret is insufficient for these cases. This is a design inference from the documented range semantics. [WebKit Input Events explanation](https://webkit.org/blog/7358/enhanced-editing-with-input-events/).

Apple documents Scribble text entry and selection/revision gestures on supported iPads with Apple Pencil; Google documents Gboard handwriting, language availability and predicted spaces. These establish real input modes worth testing, not a promise that an arbitrary custom editor supports them. Test handwriting as OS-produced text/replacement input, including scratch-delete and insertion on Scribble where available, and word/space corrections on Gboard. Recognition quality and supported language lists belong to the OS/keyboard; the editor must preserve the delivered edit and selection without loss or duplication. [Apple Scribble guide](https://support.apple.com/en-gb/guide/ipad/ipad355ab2a7/ipados), [Gboard handwriting guide](https://support.google.com/gboard/answer/9108773?co=GENIE.Platform%3DAndroid).

Physical keyboard commands require separate coverage. `KeyboardEvent.key` reflects the selected layout and modifiers; `code` represents a physical key position. Test non-US layouts, dead keys, AltGraph where available, and hardware/onscreen keyboard switching rather than treating text entry as a sequence of US-layout keycodes. Keep layout-map rejection/absence harmless and do not take over OS/browser-reserved commands. [KeyboardEvent.key](https://developer.mozilla.org/en-US/docs/Web/API/KeyboardEvent/key), [KeyboardEvent.code](https://developer.mozilla.org/en-US/docs/Web/API/KeyboardEvent/code), [getLayoutMap failure conditions](https://developer.mozilla.org/en-US/docs/Web/API/Keyboard/getLayoutMap).

## Keyboard geometry and viewport evidence

Chrome's 2022 article documents the Chrome Android 108 change to resizing only the visual viewport by default, and three `interactive-widget` modes. It explicitly excludes WebView from that change. Its older cross-browser grouping must not be reused as a current Firefox matrix. Mozilla's resolved Firefox 132 change confirms the later Android `resizes-visual` default. Qualify embedded WebViews separately if they become supported surfaces. [Chrome viewport change](https://developer.chrome.com/blog/viewport-resize-behavior), [Mozilla bug 1916002, RESOLVED FIXED, milestone 132](https://bugzilla.mozilla.org/show_bug.cgi?id=1916002).

`dvh` tracks dynamic browser UI, but the virtual keyboard is not generally included in viewport-unit changes. `VisualViewport` can shrink for either keyboard occlusion or pinch zoom; a height difference alone is not a reliable keyboard-presence oracle. The editor must handle offsets, scale, scrolling and a keyboard that does not behave like a full-width bottom rectangle. This motivates device tests for iPad floating/split keyboards, zoom and nested scrollers rather than a fixed guessed keyboard height. [web.dev viewport-unit caveats](https://web.dev/blog/viewport-units), [VisualViewport geometry](https://developer.mozilla.org/en-US/docs/Web/API/VisualViewport).

Where supported, `navigator.virtualKeyboard.overlaysContent = true` transfers occlusion management to the application. `boundingRect` and `geometrychange` expose geometry; `show()` requires a focused form control or editing host. Opting into overlay behavior without implementing occlusion handling can make the editor worse. Recommend host-level ownership of this document-wide policy, capability detection and teardown, with tests for both default behavior and the optional overlay mode. [Chrome VirtualKeyboard API documentation](https://developer.chrome.com/docs/web-platform/virtual-keyboard).

WebKit evidence requires care: the broad [259770 implementation request](https://bugs.webkit.org/show_bug.cgi?id=259770) remains **NEW**, while [296721 parsing work](https://bugs.webkit.org/show_bug.cgi?id=296721) is **RESOLVED FIXED** (landed 2025-07-31), and [321543 feature-flag enablement](https://bugs.webkit.org/show_bug.cgi?id=321543) is **RESOLVED FIXED** (landed 2026-08-13, `319118@main`). These are distinct issue scopes. They do not establish the first shipping iOS Safari version or successful editor behavior. Record a target-version result instead of claiming universal absence or universal support.

## Optional API costs and source corrections

EditContext requires the application to render text/selection, update selection and control bounds, and maintain selection state. Canvas-based use also requires caret navigation; the Chrome introduction notes that built-in spellcheck does not work for canvas. An EditContext backend therefore needs its own geometry, touch selection, accessibility, correction and undo qualification. API availability alone is no evidence that these responsibilities are fulfilled. [Chrome EditContext introduction](https://developer.chrome.com/blog/introducing-editcontext-api).

Keyboard Lock is a fullscreen-oriented progressive enhancement; it only captures keys the OS permits and must be released on exit. Do not make it an ordinary mobile typing prerequisite. Older Chrome pages say a new lock permission starts in Chrome 130, but the [permission article](https://developer.chrome.com/blog/keyboard-lock-pointer-lock-permission) was updated **2026-03-17** to say the permissions were not launched. Avoid repeating the stale permission claim; feature-detect, handle failure, and test the target browser. [Chrome fullscreen guidance](https://developer.chrome.com/blog/better-full-screen-mode).

## Proposed qualification matrix and resource ownership

Minimum physical-device coverage should include an iPhone Safari, an iPad Safari with Apple Pencil where supported, and Android Chrome plus Firefox with Gboard. Include the declared oldest supported and current release ranges, portrait/landscape, software and hardware keyboards, and at least one non-Latin composition language. Record OS build, browser build, device model, keyboard name/version/settings/language, display/zoom configuration and input hardware. This is a proposed coverage floor, not a claim that a small matrix proves every keyboard or OEM combination.

| Case family | Actions | Required observable result |
|---|---|---|
| Composition lifecycle | Candidate updates, accept/cancel, focus change, blur, block transform, remote patch and local undo while composing; dispose during composition. | No lost/duplicated committed text; coherent semantic history and selection; composition range protected or transformed under the documented conflict policy; no callbacks after disposal. |
| Corrections and replacement | Autocorrect mid-paragraph; predictive replacement; swipe/glide text; emoji/ZWJ/combining text; replace across marks; undo/redo then type. | Engine text, browser text and mapped selection converge; unaffected marks survive; replacement occurs once with meaningful undo. |
| Touch and atoms | Long-press, selection-handle drag across blocks/atoms, cut/copy/paste, toolbar action, return to typing. | Selection stays meaningful, commands affect the selected content, keyboard/focus remain recoverable, native selection UI remains usable. |
| Occlusion and geometry | Open/close keyboard; rotate with keyboard open; browser chrome expand/collapse; zoom/pan; nested scroll; iPad floating/split keyboard where available. | Caret and active controls stay reachable without scroll oscillation, incorrect coordinate conversion, involuntary zoom reset or keyboard-height assumptions. |
| Hardware and accessibility | Attach/detach hardware keyboard; layout changes; shortcuts; Tab/Escape; touch screen-reader editing with VoiceOver/TalkBack. | Plain input and command alternatives remain available; focus is not trapped; composition/OS commands are not stolen. |
| Lifecycle and load | Repeat mount/focus/type/blur/unmount; switch two editors; background/resume; long document plus continuous input/selection. | Listeners, observers, timers, animation frames and document policies have bounded ownership; input is responsive under the declared measured device envelope. |

Use deterministic fixtures for normalization, mutation reconciliation, offset mapping and optional-API absence/rejection branches. Synthetic events, replayed traces, responsive emulation and desktop automation establish those tested paths only. They cannot substitute for OS composition, native selection handles, actual keyboard occlusion, handwriting or physical-device latency measurements. Record executed/passed/failed/skipped counts per evidence layer; unavailable hardware is an explicit gap, not a pass.

Recommended ownership is explicit: the **host** controls document viewport metadata, page scroll policy and optional VirtualKeyboard overlay mode; the **web adapter** owns DOM/selection mapping, geometry observations, input listeners and cleanup; the **engine** owns portable edits/history without browser-specific policy. Coalesce geometry work, separate layout reads from writes, bound mutation reconciliation to the affected region, and avoid full-document rewrites during active composition. These are proposed engineering requirements, not measured optimizations. Numeric input-latency, frame-time, memory and bundle budgets must be declared and measured on the actual supported device envelope; this research supplies no invented benchmark results.
