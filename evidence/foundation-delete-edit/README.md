# Delete versus edit probe — FND-1.7

Implemented and locally verified with real Yrs replicas and local update transport; not a production schema or deployment. Immutable source revision and tested working-tree hashes are in `receipt.json`. Source/live roadmap unchanged.

The disposable policy uses one persistent true tombstone per logical block ID. Deletion removes the block from the visible projection, retaining its original registry rich text and placement. A separate explicit recovery projection exposes current hidden content, marks, UTF-16 length and the original text identity. Concurrent updates continue to merge into this content; receiving edits never clears the tombstone. A local edit against a known deleted target rejects before mutation. Repeated delete and recovery reads leave update bytes and state vector unchanged. No restore command, undo or garbage-collection policy is qualified; those must be resolved before such production behavior is claimed.

`core/crates/editac-core/tests/delete_edit_probe.rs` composes `tests/support/delete_edit.rs` with the selected stable-registry harness. Fixed input `a😀b` has bold emoji at UTF-16 [1,3). Two reversed writer-ID assignments race deletion with an italic insertion: visible content is absent, recovery is `a😀!b` with original identity. Causal edit-before-delete produces that same recovery. A third-replica disconnected case includes a dependent delta replacing the complete emoji surrogate pair with code-marked `👩‍💻`, plus an independent underlined RTL insertion: recovery is `a👩‍💻!bאב` with exact expected marks and original shared text identity. All nine writer replicas have explicit semantic assertions.

All 138 observer arrival permutations are enumerated (6 + 6 + 6 + 120), including updates arriving before initialization and dependent deltas before prerequisites. Every update is duplicated, reverse-replayed and restored into a fresh replica. Each final visible/recovery projection matches the documented expected text, marks, placement and identity; reads emit no repair writes. These are real Yrs merge/snapshot boundaries, not prepared semantic answers. `artifacts/` holds five projection/schedule traces and fifteen v1 updates; hashes and byte counts are in the receipt.
