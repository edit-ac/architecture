# Canonical document durability

Authority: [single-format decision, 2026-10-23](../decisions/006-single-format-before-publication.md). This is the production target and durability review, not a declaration that every cutover, crash test or final suite has passed.

## Canonical identity

Use schema `editac.registry.editor.v5`, profile `editac.yrs-yjs.editor.v5`, protocol 1, Yrs/Yjs update encoding 1 and UTF-16 public offsets. `DocumentIdentity::current` is the application-facing selector. Keep document ID and epoch as separately validated stable UUIDs. SDK version, build revision, process ID and current writer ID must not become document-format identity. The current v5 roots, immutable source identities and witnessed split/join semantics are the normative layout; older spec references describe the origin of those rules, not additional supported runtimes.

Keep the existing v5 identifiers for already written canonical checkpoints. A cosmetic rename to v1 would create an unnecessary data boundary. All production creation, restore, sync, Session/FFI, WASM, converters, native and terminal consumers must select this same current identity. Unknown, retired or mismatched schema/profile/protocol/encoding/offset tuples reject before live mutation. Do not guess a format from root names, retry an older reader, or silently relabel bytes.

## Required persistence invariants

1. Store the exact identity and explicit initialized state with checkpoint bytes. Restoring an empty document must never rerun initial content import. Authorize creation once per new document/epoch; initialized empty data is existing data.
2. Preserve checkpoint and journal bytes until their validated replacement is durably committed. Replay duplicate/reordered updates idempotently, reject missing binary dependencies rather than accept partial state, and acknowledge persistence only at the owning durable-store boundary. A CRDT state vector alone is not a durable-save receipt.
3. Reopen with a fresh independent writer identity, preserving integrated original text identities, Unicode/UTF-16 anchors, retained owners, formatting, table/asset/reference metadata and unknown bounded data. A process writer is provenance, never a restored writer lease. Keep semantic document revisions/history; they are real user data.
4. Validate identity, tuple shapes, immutable operation records, limits and permissions on a staged replica before applying to the live replica. Failed restore, replay, command preparation or format admission must leave content, history, pending receipts and persisted recovery bytes unchanged.
5. Keep split/join presentation witnesses immutable. Later formatting, code-language changes, undo/redo, peer update order or checkpoint reopen must not reinterpret previously committed ownership. Preserve dormant/absorbed text, marks and recoverable intentions. Fresh invalid operations still reject atomically.
6. Preserve unknown bounded JSON/opaque feature data through reopen, sync, supported export and disabled-extension round trips. Unknown data grants no editing/execution permission. Malformed known records, depth/byte/operation overflow, non-finite values and forged incompatible witnesses reject with typed errors, without lossy fallback or repair writes.
7. Durable storage, schema and application upgrades must not be keyed to one development Git hash. Hashes authenticate a test or artifact; they do not authorize a document write or require the exact old build to reopen the same supported format. Capability permission/availability remains distinct from format admission.

## Independently mergeable table target

DRA-1.1 selects [table-merge.md](table-merge.md) as the single pre-publication editable-table representation: stable table/axis/cell identities, immutable per-scope records and named per-cell-block CRDT text roots. The root inventory below describes the existing runtime baseline; DRA-1.2 must implement the additional validated record/text namespace, scoped command/projection/history consumers and exact internal round trips together. The descriptor's consumer matrix is mandatory acceptance, not an implementation claim. Earlier whole-table descriptors cannot remain a second production reader after cutover. Table-free same-format checkpoints stay admissible; incompatible written table data requires separately reviewed explicit offline adoption into a fresh epoch, preserving original bytes. Never migrate or relabel on open. See the descriptor's deterministic inputs/expected merges, conflict inventory and bounded refusal rules. Retained table roots are also inputs to DRA-1.4 lifetime design; journal rollover alone does not retire them.

## Review and required proof

Source review of `core/crates/editac-core/src/document.rs`, `editor.rs`, `editor_replay.rs`, `core/crates/editac-session/src/locator.rs` and the v5 specification found existing initialized-checkpoint envelopes, staged restore/admission, document/epoch matching, fresh writer leases, binary/graph bounds and witnessed replay. These are suitable foundations. Production still admits older experimental identities and carries profile-dependent replay/projection paths; removing them is a required implementation task, not a completed review result. Versioned historical mappers remain useful independent fixture oracles, outside production dependency graphs.

Focused cutover proof must cover fresh current creation; empty and Unicode checkpoint reopen without reseeding; checkpoint plus duplicate/reordered journal replay; wrong document/epoch and retired/future tuple rejection with byte-for-byte nonmutation; witness immutability under format changes and undo/redo; unknown/opaque data retention; stale target/anchor safety; crash/atomic commit recovery; and a current-format checkpoint crossing actual Rust/WASM/Session/native consumer boundaries. Keep existing independent Yjs exchanges and semantic oracles. Test old envelopes as unsupported inputs, without compiling their readers into the runtime. Port original regression assertions to current fixtures rather than count historical old-reader passes as current proof.

Use deterministic fixtures and mocked transports only. Full functional, storage/crash, cross-runtime and native suites retain their existing final-testing owners; the focused cutover gate protects subsequent implementation without replaying every suite. Exact counts, input/artifact/runtime pins, failure dispositions and remaining unsupported claims belong to ignored progress, not generated Git evidence. No prepared provider result proves model quality, usage or launch readiness.

## Current layout and storage ownership

The current layout is the witnessed layout specified in [schema-v5](schema-v5.md). The inherited root definitions below describe that single layout, not permission to open an earlier envelope. `editor_replay::ROOTS` is its production root list; `document::ROOTS` is an older five-root list and must not be mistaken for the current descriptor.

| Y.Map root | Retained value |
| --- | --- |
| `registry-parents` | Immutable original source `n:` → `block`, or container `c:` → `list` / `quote` |
| `registry-texts` | Original source → one persistent nested Y.XmlText; never a copied text for a split/derived owner |
| `registry-placements` | Immutable initial `[parentId, order]` for an original source/container |
| `delete-probe-tombstones` | Permanent true for a deleted owner/container |
| `registry-block-attributes` | One complete presentation/content tuple per original/derived owner; bounded opaque values remain data |
| `registry-ownership-ops` | Immutable operation ID → split/join/place tuple, including complete split/join presentation witnesses |
| `registry-owner-origins` | Original text source → true; excludes containers and derived owners |
| `registry-container-attributes` | Complete list/quote tuple, including integral ordered start 0…2147483647 |
| `registry-list-item-attributes` | Owner → `["check", boolean]`; absent means unchecked |
| `registry-entity-controls` | Entity/operation → `["enabled", boolean]`; absent means enabled |

`InitializedCheckpoint` stores the full `DocumentIdentity`, explicit `initialized`, provenance `writer_id` and update-v1 bytes. `ReplayUpdate` carries the same complete identity and bytes. Split records have seven fields including the binary relative cut and left presentation witness; join records have seven fields including both presentation witnesses. Their exact shapes and place semantics remain in schema-v5. Document/epoch, source identities, operation records and actual undo/revision data are durable semantics; an SDK build hash is not part of this envelope.

Storage adds its own atomic publication and receipt boundary without changing the document format:

- Browser `packages/web/src/storage/{journal,checkpoint,transaction}.ts`: IndexedDB journal/outbox and latest/previous checkpoint publication, coverage and checksums. Recovery verifies entries and replays even covered journal updates through the Rust restore callback. Database name is host-selected (adapter default `editac-local-storage`), scoped to the browser origin/profile.
- Session `crates/editac-session/src/{ports.rs,store/mod.rs}`: typed update/receipt identities include the entire admitted document tuple, writer, sequence, origin and byte checksum. NativeStore uses an explicitly supplied absolute SQLite path, application ID `0x45414353`, store version 1, WAL, FULL synchronization and transactional state. Recovery validates latest/previous candidates and retained journal; SQLite/store version is a separate storage contract.
- CLI `src/storage.rs`: an explicitly selected recovery directory, latest/previous checkpoint, retained journal/outbox and durable receipts; success requires file sync, atomic rename and directory sync. `src/local.rs` defaults to `.editac-recovery/<documentId>` beside the edited file. It does not establish a global application-data directory. The document-store service also requires an explicit `--store` path.

### Concrete unresolved data-safety findings

1. **Retired runtime admission and dispatch remain.** `DocumentIdentity::validate` admits v1–v4 pairs; `has_*`, root registration, `editor.rs` and `editor_replay.rs` still dispatch by profile, and production replay imports the fixture-owned bounded decoder. This is observable current source, not completed cutover. Implementation owners: SFC-2.1, SFC-2.2, SFC-2.3, SFC-3.1, SFC-3.2 and SFC-4.2; consumer convergence SFC-3.3; rejection/retention proof SFC-5.1. Port negative old/future-envelope assertions without retaining their positive readers.
2. **Concurrent edits to distinct table cells can overwrite each other.** `commands::table` derives a complete table tuple from `expected`; `commands::editor` publishes it as one `registry-block-attributes` map value, including cell edits. `table_shape::concurrent_shape_and_cell_writes_converge_without_projection_repairs` deliberately accepts any single authored tuple as the merged result. Convergence therefore does not prove preservation of independent cell edits. This is a source-confirmed representation risk, not a newly executed lossless-concurrency qualification. Implementation ownership is the shared content/command boundary SFC-3.2, with retained-data projection SFC-3.1 and consumers SFC-3.3; SFC-4.1, SFC-5.1 must preserve existing atomicity assertions and add independent-cell retention proof. Do not silently rewrite existing table bytes or claim the current whole-tuple model merges cell intentions.
3. **Bounded records do not yet provide a document-lifetime rollover policy.** `editor_replay::project` rejects more than 4096 retained sources or ownership operations (8192 controls/spans); disabling an operation retains its record. Session `StoreLimits` defaults to 4096 journal records; CLI `MAX_ENTRIES` is 4096 and scans retained entries even after checkpoint publication. Browser checkpoint recovery likewise replays all covered entries. A checkpoint alone neither compacts retained operations nor supplies remote receipts. Owner SFC-2.2 must distinguish journal/coverage retention from safe recovery, SFC-2.3 owns retained replay limits, SFC-3.2 owns history preservation, and SFC-5.1 must carry this unresolved lifetime risk into final storage/resource qualification. The 4097th journal record and the 4097th structural operation are different limits and need separate deterministic boundary/continuation proof. Never solve either by clearing the journal, dropping recoverable intentions, raising caps without resource proof or reseeding a new document on open.

These findings are handoff obligations within the existing gates, not new runtime compatibility requirements or proof that a same-format real-data conversion is necessary.

## Development-data discovery and conversion decision

For SFC-1.2, inspect configured explicit store paths and file-adjacent `.editac-recovery` directories first, then the browser origin/profile used by development examples. Record only path, file metadata, safe container headers, exact byte hashes and whether the source remained stable during read-only inspection. Distinguish real documents, unclassified origin stores and deterministic test outputs; a localhost LevelDB container alone does not prove an edit.ac schema or a legacy document. Do not open a candidate through an application path that can initialize, repair, migrate or write it. Browser credentials, document text and opaque content are outside this inventory.

The bounded local inventory and source pins belong in the ignored SFC-1.2 progress receipt. No identified real legacy checkpoint currently establishes a conversion requirement; synthetic v1–v4 fixtures do not create one. Preserve unclassified browser/store candidates as original bytes and do not infer that data outside the inspected/configured roots is absent. No converter, reset or runtime fallback is authorized or required by this review.

If real incompatible data is later identified, stop before adoption and review a separate offline operation: hash and preserve original checkpoint/journal and sidecars; take a consistent read-only copy; decode using a fixture/offline tool outside production; validate text, marks, original ownership, unknown data and actual history; create a separate destination with an explicit fresh epoch; compare semantic/opaque results and rehearse failure recovery; adopt only after review, retaining the untouched original. A cosmetic schema relabel or in-place overwrite is not conversion.

## Publication boundary

Before publication, review the complete format descriptor and dependency/decoder versions, prove recovery/unknown-data retention and complete the applicable suites, then explicitly freeze the published identity. Future format changes require a documented compatibility or offline migration plan tied to real published data, not a new production version for each development experiment. Offline conversion preserves original bytes, creates a new destination/epoch and proves semantic/opaque-data preservation before adoption; it never runs implicitly on open. Physical-only qualification is separate from the accepted simulator/emulator/OS-host evidence required for native readiness.
