## Document addressing

Document identity comprises opaque document ID, epoch/session and schema profile. Source identity is separate: a filesystem path, cached document, or configured authority locator can refer to the same document. Moving a file does not silently clone its collaboration identity; copying/importing creates a new explicit identity unless the host intentionally links it.

The frozen v1 locator grammar accepts `ac://<document-id>` for catalog resolution and `ac://<authority>/<document-id>` for a configured authority. Document IDs and epochs reuse the engine's canonical lowercase 36-byte hexadecimal UUID grammar. IDs are opaque, case-sensitive identities, not short hashes or content addresses. Uppercase UUIDs, Unicode (including normalization variants), percent encoding (including double encoding), whitespace, backslashes, dot segments, extra separators, userinfo, ports, queries and fragments reject rather than being decoded or silently normalized. Version queries are unsupported in v1. Canonical formatting round-trips the exact accepted form. Authorities are lowercase ASCII names of 1–63 bytes, starting with a letter, containing letters/digits/hyphens and ending with a letter/digit. They are host configuration keys, not arbitrary network hosts.

HTTPS app links are accepted only as `https://<configured-host>/ac/<document-id>` after the host explicitly maps that exact lowercase DNS host to a configured authority. DNS labels are 1–63 ASCII letters/digits/hyphens, without leading/trailing hyphens; the whole host is at most 253 bytes. No credentials, ports, queries, fragments, alternate prefixes or implicit redirects are accepted. Both input forms feed the same catalog resolver. Registering an authority or app-link host performs no network access and stores no credentials.

The local catalog maps an exact locator to a complete engine document identity (document ID, epoch, schema, profile, wire and offset metadata) and a host-selected source binding. Multiple locators may explicitly link to the same identity. Conflicting epochs/profiles for one document ID reject, including across authorities; rebinding an existing locator is not an implicit replacement/migration API. Local paths enter through a separate typed host-granted binding, never through URI text. The host must perform filesystem permission checks before inserting that binding. Moving a path is a host catalog operation; copying/importing requires explicit new identity. Engine profiles are validated using existing constructors; no schema migration is inferred.

Resolution is a read-only catalog lookup returning local/cached/hosted/locked/unavailable/unauthorized/incompatible outcomes. Unknown authorities reject even when an identically named document exists locally. An uncached hosted mapping returns unavailable offline and hosted metadata online; neither outcome fetches, initializes or creates a document. Cached populated and initialized-empty documents resolve identically, preserving their explicit existing identity. Policy states precede readiness. The resolver has no transport or document-creation port; a later lifecycle implementation must still restore/validate the actual checkpoint before editing. A locator contains no password, token or encryption key. Resolving arbitrary hosts or file paths cannot bypass host allowlists, path permissions or SSRF policy. Displaying or importing a link never performs an implicit network fetch. Launching an OS deep link requires host registration/activation policy; it cannot execute a shell command from URI text.

Executable grammar and catalog fixtures: `core/crates/editac-session/tests/locator.rs`, delivered under CAP-1.2-I1/V1 (the original parent acceptance remains unchanged).

## Local-first session

Provide a portable session companion to the engine with LocalStore, Transport, SourceResolver, AuthorizationPolicy and optional HistoryStore ports. IndexedDB, native transactional storage and CLI recovery implement the same journal/checkpoint/outbox conformance cases, without forcing a database crate or browser runtime into the semantic core. Promote CLI/native duplicated lifecycle logic into this shared boundary.

Opening a cached document first restores local state, then enables editing and optionally attaches networking. Creating a local document is offline and idempotent; subsequent hosting assigns an explicit authority mapping rather than re-importing content. An uncached offline hosted target returns unavailable. Local commands, undo/redo and readonly views never wait for a socket.

Expose restoring, ready, unsaved/pending local, locally committed, pending upload, synchronized-but-durability-unknown, remotely committed, conflict, locked and recovery-required states. Connectivity is orthogonal to durability. A completed local transaction is not an upload receipt. Native suspend/termination and browser tab close use the same recovery contract, without relying on an unload handler.

Sharing a database is not live synchronization. Cross-tab/process adapters exchange committed updates with distinct writer/client IDs and echo suppression. Test a pair of offline local clients plus reconnect to a hosted peer. Backpressure bounds memory and preserves an outbox rather than dropping acknowledged edits.

Hosts define offline authorization policy/leases. Offline revocation cannot retroactively remove already acquired plaintext. An expired policy may block further writes while retaining recovery data; a host cannot promise both unrestricted offline writes and instantaneous remote revocation. Upload always rechecks server authorization. Readonly is enforced by every mutation entry point, including MCP and imports, not just controls.

### Lifecycle v1 (CAP-1.5)

`editac-session::session::Session` owns one live engine replica and a `SessionStore` writer reservation. Open resolves local/cached catalog metadata and validates the real initialized checkpoint plus the full retained journal before returning a handle. There is no socket, fetch, credential discovery or automatic empty initialization. Explicit local creation publishes an initialized checkpoint through generation-zero CAS; repeated creation against an initialized store restores that identity and ignores proposed seed content. A corrupt existing store never becomes a new document. Failed creation retains its seed in a recovery-required handle; a competing successful initializer is a conflict requiring reopen, never a merge of independent seeds. The host owns exclusive store creation/path grants. Each restored writer is freshly reserved, with bounded collision retry before admission. Memory reservations are volatile and shared by clones; native reservations remain in SQLite.

Synchronous open returns ready or an error (locked/unavailable/unauthorized/incompatible/store/engine); it does not advertise readiness before restore. Handle state reports readiness, local transaction capability/result, pending upload count, remote receipt evidence, conflict, transport connectivity, cached permission and transport authorization independently. A completed send is labeled sent with durability unknown and retains every pending record; queue acceptance alone does not establish peer synchronization. Remotely committed means all currently admitted durable journal records have exact authenticated negotiated receipts; an empty new document or an attached socket cannot imply it. A reopen can recover that historical receipt evidence while remaining detached. No stronger durability than the selected store capability is claimed.

Hosts supply a `CachedPermission` and an explicit clock in the same domain on each edit/history call. Writable permission with no expiry grants offline writes; an exclusive expiry blocks new edits, undo and redo at or after that time. Readonly denies all those paths without mutation. Policy replacement is an explicit trusted-host action, not a document field. Transport attachment requires a separate unexpired host authorization lease and an authorized transport, after local restore. Every flush and receipt rechecks its lease and connection; detached/disconnected/expired authorization preserves durable pending work. Hosts must report server rejection through transport state or detach. An independent valid cached permission may continue offline edits after transport auth expiry; no instantaneous offline revocation promise is made. Reopen must receive fresh host policy; leases/credentials are not stored as semantic document content.

All exposed mutation paths use existing engine text/history commands on the handle's serialized mutable owner and atomically append their exact owned updates before local acknowledgment. Immutable engine reads do not grant a mutable escape. Edit-service/module/provenance expansion stays in CAP-1.8/1.9. Append failure retains the already admitted update and freezes further mutation, transport attachment, flush and receipt publication. Reads and a labeled, unacknowledged recovery export remain available. Recovery retries the exact update idempotently, validates latest/previous checkpoint plus full journal, then replays validated durable state into the owner and refreshes outbox/sequence/receipt state before unfreezing; local undo history is retained. Settlement of an already admitted operation does not require a renewed write lease. Receipt transaction failure also freezes publication until recovery resolves its durable membership. Recovery never overwrites the store with an unjournaled full-state checkpoint. Incoming transport application is not exposed by this lifecycle gate; later delivery work must use the same admission barrier. Send errors/backpressure preserve the outbox and do not become save claims.

Canonical qualification is `cargo test -p editac-session --test lifecycle --locked`, with identical offline creation/edit/history, cached permission/expiry and transport auth/receipt fixtures over memory/fault adapters and, with `native-store`, actual SQLite. Native connection reopen and persistence-failure recovery supplement the retained CAP-1.4 crash/full-disk qualification. No deployed transport, power-loss or physical-device release qualification follows.

### Native shared Session ownership (NSR-1.1)

`editac-ffi::NativeSession` adds the actual shared `Session<Arc<NativeStore>>` and `EditService` to the existing UniFFI 0.32.2 library. It is distinct from the existing preparation-only `NativeEngine`: no second engine bridge, Session semantics, storage implementation or Swift adapter is introduced. The host grants an absolute SQLite path and canonical v5 document/epoch identity. `createLocal` exclusively creates a new file; `open` only restores an existing store and never initializes an unsuccessful restore. Creation can return a recovery-required handle when initial publication fails, as the shared Session contract requires.

One private Rust worker constructs, owns and drops the Session, native store, history and prepared edits. Aliases share its bounded synchronous submission lock/channel. `dispose` is idempotent, waits for an accepted operation and joins the worker; all other calls, including cancellation, subsequently return `Disposed`. Final-reference release also joins. No foreign callbacks are exported, so there is no callback queue after disposal. Owned reads, revision/checksum bytes and recovery buffers remain usable after release. Hosts schedule expensive synchronous calls away from their UI thread.

`prepareEdits` translates a bounded whole-edit batch of UTF-16 node ranges into existing `EditorCommand::ReplaceAt` commands and calls the shared `EditService` planner against an observed revision. It retains at most 128 opaque, writer-scoped, single-use plans; no preparation mutates live state. `commitEdits` consumes the token even on failure and rechecks current permission, revision and service admission before the shared Session mutation/journal append. `cancelEdits` serially releases an uncommitted plan, is idempotent for unknown tokens, and cannot interrupt or roll back an accepted commit. Undo/redo use the same service and revision/permission barrier. Trusted host permission replacement is explicit and serialized; clocks are host-supplied.

`read` exposes a minimal owned text presentation (node ID/kind/text), optional observed revision (absent while recovery-required), local durability, pending-upload count, recovery error and apply/history capabilities. It is not a full rich-platform projection or remote receipt claim. `recoveryExport` labels the actual shared Session checkpoint and optional unjournaled update with `locallyCommitted`; an unsaved salvage buffer is never a durable acknowledgment. `recover` retries the retained exact update using the existing Session recovery path. Store failures preserve all `PortError` variants, including quota, conflict, integrity and commit-unknown, as a typed native enum. Session permission/readiness and revision failures retain distinct typed cases; engine/document/history failures retain their owned diagnostic messages.

Qualification is deterministic Rust execution of `editac-ffi` native Session integration and internal SQLite fault/lifetime cases. Generated Swift execution, AppKit-owned scheduling and view-disposal tests remain NSR-1.2 and original DSK-1.3; no SDK, IME, release, power-loss or deployed transport qualification follows from this boundary.

### Explicit local delivery v1 (CAP-1.6)

Local channels are host-granted, document/epoch/profile-scoped wake notifications over a shared committed journal, not a database polling promise or a durability receipt. After a successful append, a sender signals its fresh live writer ID. Recipients read and verify the full retained journal, qualify a combined real-engine candidate, then apply remote updates without manufacturing local typing history or echoing them. An explicit startup/reconnect catch-up replays missed notifications; channels do not erase journal/outbox entries. Concurrent checkpoint publication remains generation CAS and retains full replay coverage. Hosted reconnect accepts a scoped, engine-qualified journal envelope before durably appending and applying it; send success is still durability unknown.

Native Unix datagram adapters use an explicitly host-owned socket path and bounded peer list/drain. A notification contains a scoped digest and writer ID only; untrusted/spurious hints cannot supply semantic bytes. Full/missing queues report backpressure/unavailable and preserve committed work for catch-up. Hosts own peer discovery, permissions, event scheduling and abandoned endpoint cleanup; no network socket or implicit authority lookup is involved. Browser adapters use an explicitly named BroadcastChannel, serialized/coalesced replay and a committed-only lifecycle observer. Startup/reopen catches up from IndexedDB; disposal removes listeners/closes the channel. Browser local-channel input is bounded metadata, never a source of plaintext updates or authentication.

Canonical checks: `cargo test -p editac-session local_channel --locked`, the same check with `--features native-store` for actual SQLite/process sockets, `npm run build`, and `node --test tests/local-channel.test.mjs` for actual offline tabs/BroadcastChannel/IndexedDB. No deployed server or power-loss qualification is implied.

## Portable store and transport ports (CAP-1.3)

The session companion owns detached journal entries and frames. A journal entry binds the full engine document identity (document/epoch/schema/profile/protocol/encoding/offsets), nonzero live writer ID, positive monotonic writer sequence within the browser exact-integer range (1 through 2^53−1), origin and SHA-256 update digest to owned immutable bytes. A duplicate key with identical content is idempotent; different content/origin or a sequence gap rejects. Writer IDs are routing/provenance, never authentication. Adapters must allocate distinct live writer identities and translate browser receipt strings without weakening exact tuple comparison; typed Rust IDs do not change the existing wire protocol.

LocalStore operations serialize within a shared store instance; native adapters must also serialize across processes. Session admission uses one serialized owner for semantic preparation/commit and durable capture; the engine Document and its listeners/history are not Send, so threaded hosts marshal owned requests to that owner rather than moving the live replica across threads; sharing a database alone does not supply semantic admission or local delivery. Append atomically journals an entry and makes it pending. LocalCommit is returned only after transaction completion, with actual durability capability. The memory and fault adapters report volatile durability and qualify prepared behavior only. A lost post-commit acknowledgment returns CommitUnknown; recovery or exact idempotent retry resolves it without double admission. Before-write/before-commit failures leave the prior state intact. Typed quota, permission, unavailable, conflict, integrity, incompatible, resource-limit and commit-unknown outcomes are recoverable host states; no error becomes a save acknowledgment.

Checkpoint publication compares a non-reused publication generation inside the transaction, binds the full initialized engine checkpoint plus exact unique committed coverage identities into a SHA-256 manifest, and atomically retains the previous valid checkpoint. Coverage is not proof of semantic inclusion: the engine/session supplies it. Recovery verifies all journal bytes and attempts latest then previous, returning rejected-checkpoint diagnostics and every journal entry, including covered entries, for idempotent engine replay. It also exposes the verified previous envelope when present: if semantic engine decoding rejects latest despite a valid manifest, the session can try the previous envelope plus full tail without inventing an empty document. Storage integrity does not replace engine schema/CRDT validation. Neither checkpoint publication nor receipt acceptance deletes journal bytes. This conservative retention policy is bounded by configured record counts and serialized-payload byte limits (metadata/allocation overhead is additional); compaction needs separately qualified policy. A missing valid checkpoint is recovery-required, never a new empty document.

Pending membership changes only when the host supplies a durable receipt from the negotiated editac-durable-receipt-v1 application transport matching the complete scope, writer, sequence and digest. Unknown/wrong-scope receipts cannot prune anything. Absence of capability means remote durability is unknown; sync and awareness are never receipts. Receipt acceptance itself completes a local transaction. Adapters import stored records against their retained digest/manifest rather than rehashing them as new records, and revalidate immutable journal content on recovery; corruption must not be silently omitted.

Transport attaches explicitly under host authorization to an existing scoped session. Owned sync/awareness frames have configured frame-byte, queue-byte and queue-count bounds; backpressure returns an error, leaving the durable outbox available for retry. Disconnected/unauthorized/incompatible states are explicit. Presence is ephemeral, not journaled or durable. Prepared transports exercise these contracts without a network service; native/browser adapters and lifecycle authorization remain later gates.

Native-store compatibility decision: use a session-owned SQLite WAL adapter in CAP-1.4, with explicit host-selected sidecar/store path, full synchronous transactions, per-writer allocation, atomic journal/outbox/checkpoint/receipt operations and cross-process compare-and-swap. Keep SQLite out of editac-core and behind an optional native session feature. The CLI has no existing store to reuse. SQLite guarantees require actual process termination/full-disk/transaction-boundary qualification in CAP-1.4; no filesystem, power-loss, eviction or release claim follows from memory fixtures. No new document schema, migration or wire promise is introduced.

Native adapter v1 (CAP-1.4): `editac-session` exposes `store::NativeStore` only with the optional `native-store` feature (default features stay empty). The host supplies an absolute filesystem path, validated/granted separately from locator text, with existing parent directory on a local filesystem supporting SQLite locking. `create_new` exclusively creates that file; `open_existing` never creates a file, schema or checkpoint. Keep `<path>-wal` and `<path>-shm` alongside the database; copying only the main file while live is unsupported. Unknown application IDs/store versions or mismatched full scope reject without migration. SQLite WAL uses FULL synchronous transactions, with fullfsync/checkpoint_fullfsync requested; the capability is process-crash durability, not independently qualified power-loss or network-filesystem durability.

Native persistence reuses the portable memory policy over a detached verified snapshot inside each SQLite transaction. A bounded, versioned local snapshot holds all journal/checkpoint/outbox/receipt records atomically; it is adapter data, not a new semantic document or wire format. JSON encoding/SQLite pages add overhead beyond payload limits. Reads use a single snapshot transaction; writes use BEGIN IMMEDIATE across processes. Retained generation CAS, previous valid checkpoint, immutable digests/manifests, full replay tail and exact pending receipts keep the portable semantics. Invalid latest checkpoints fall back without resetting publication generation. An absent valid checkpoint remains recovery-required. No compaction or automatic database replacement is offered.

Before its first append, a host reserves its actual engine replica writer ID with `claim_writer`; zero or an existing reservation rejects. Reservations are persistent, bounded by record capacity and never reused after termination. A restored replica generates a fresh engine ID; if it collides with a retained reservation, restore a fresh replica and retry before editing. The host owns admission to that writer, not authentication by the ID. Unreserved appends reject. Interrupted reservation acknowledgment is resolved by recovery/fresh identity, never by silently assigning an old writer to a new replica. Per-writer journal sequences survive reopen. Transaction completion precedes every acknowledgment; commit errors/lost acknowledgments conservatively return CommitUnknown and require recovery/idempotent retry. Explicit diagnostic observers/fault hooks and connection-local SQLite page quotas (reapplied on reopen) support deterministic boundary qualification; no environment variable enables faults in production.

## Revision and edit admission

Return opaque revision tokens bound to a specific document/epoch/schema/profile and immutable observed state. A Yjs state vector alone is insufficient because deletions can change visible state without advancing the same clocks. Choose and test a persisted generation/content-state validator including deletion effects; tokens are not globally ordered wall clocks.

Compare expected revision and prepared preconditions within the serialized commit boundary. Equality protects the endpoint's observed state; it is not a global lock against offline peers whose updates arrive later. Surface subsequent merged changes normally. No direct `replaceDocument(markdown)` shortcut is allowed to defeat source reconciliation.

The shared editor service exposes read snapshot/capabilities, prepare semantic commands or source changes, preview, apply, observe changes and receipt lookup. It uses FMT-1.12's exact baseline/source-to-identity mapping. Unsupported or ambiguous mappings return recoverable base/proposed/current data. Capability checks include document permissions, module support, readonly/history mode and resource limits.

A post-commit persistence failure enters recovery mode: freeze further mutation admission and outbound synchronization until ordered durable recovery succeeds. Keep reads and labeled recovery exports available; bound queued incoming updates. Later human edits, checkpoints or full-state synchronization must not publish an unjournaled predecessor. When the predecessor is an agent request, its durable dedup receipt belongs to the same publication barrier; see the host-agent contract.

## Operation identity and history

Each admitted operation has a request/operation ID, authenticated actor supplied by the host, origin, affected identities and observed before/after revision. Actor metadata from document prose or a client-supplied display name is not trusted attribution. CRDT client IDs alone are not authenticated authors.

History origin policy separates local human gestures, other humans, agent operations, imports and replay. Agent operations can be reviewed/reverted as authorized new changes without becoming unintended human typing undo groups. Cross-client operation records feed diff/history views, but are not described as a tamper-proof audit ledger without additional evidence.
