## Keep the shared core small

| Layer | Required responsibility | Admission boundary |
|---|---|---|
| Rust semantic core | Prepared commands, stable anchors, command applicability, directional selection, Unicode boundaries, history and scoped patches | Add a primitive only for a missing reusable semantic operation; qualify schema/ABI changes first. Viewport, pointer, keyboard geometry and browser permission state stay outside Rust |
| Required web adapter | Native editable input/selection, minimal touch-safe focus/scroll integration, bounded event reconciliation, usable baseline controls and lifecycle cleanup | Reuse existing adapter exports and a single document model; avoid a separate mobile runtime, alternate CRDT or global gesture framework |
| Shared browser services | Disposable viewport/occlusion snapshots, overlay scheduling and focus/selection leases used by multiple presenters | Share a small service only when at least two consumers need it; otherwise keep the implementation local. Scope ownership to the mounted document/window, not a global singleton |
| Optional capability adapter | VirtualKeyboard geometry, host-requested keyboard facilities, richer pointer gestures and browser import/share services | Feature-detected and capability-gated; absent/denied/error paths retain baseline editing. Load implementation and dependencies only when requested |
| Optional extension presenter | Tables/code tools, slash/reference panels, asset/embed controls, reorder/resize and assistance UI | Own only transient interaction/presentation; call shared semantic commands. No disabled-extension listeners, assets, workers or requests |

The core does not need a new character model, persistent touch state, keyboard-height field or mobile-specific block type. Adding an API abstraction requires a demonstrated behavior/fallback need and a fixture; do not wrap every browser API preemptively. Device capabilities can change during a session: external keyboards, trackpads, stylus, split-screen and orientation. Coarse pointer/hover media queries and pointerType are hints, not exclusive device identities. Do not use user-agent names as the primary routing mechanism; a narrowly documented browser workaround needs an exact affected-version fixture and removal condition.

## Touch, selection and gesture ownership

Preserve native tap placement, double/triple-tap selection where provided, long-press selection handles, context menus, scroll momentum, pinch zoom and OS edge gestures. Use the actual Selection and input events to map the resulting semantic range. Rendering and remote patches must not replace the composing or actively selected subtree. Native handles/context menus may cover application controls; provide another reachable toolbar/command route rather than suppressing the native menu across the editor.

The editable root remains text-selectable and scrollable; do not set global `user-select: none`, disable zoom or apply `touch-action: none` to the editor/page. Prefer Pointer Events with a documented fallback for a claimed browser without them. A gesture handle may own a small declared touch-action region; declare it before the gesture begins. Use passive listeners when no cancellation is needed. `preventDefault` is local and conditional; synthetic event cancellation does not prove actual mobile scrolling behavior.

Optional drag/resize starts only on its dedicated handle after the declared activation threshold. Track pointer ID, capture owner and gesture state; ignore unrelated pointers. `pointercancel`, unexpected `lostpointercapture`, a competing second touch/pinch, native scroll takeover, unrecoverable orientation/zoom/host geometry change, blur, read-only and disposal cancel provisional work without a document mutation. Successful pointerup commits at most once; later click/capture-loss cannot duplicate or roll back the completed command. Release capture, auto-scroll and listeners on every terminal path. Owned gesture auto-scroll and ordinary reconcilable geometry updates refresh coordinates without self-canceling; stop only if the target/coordinate state cannot be safely revalidated. Temporary geometry and hover destinations are not CRDT updates. Each drag operation also has a tap-based action (for example Move before/after or an explicit size choice), plus a keyboard route; keyboard support alone is not the non-drag pointer alternative.

Controls meet applicable WCAG 2.2 target-size/spacing requirements; use 44×44 CSS px as the preferred touch target where practical, while documenting the 24×24 CSS px AA minimum and its exceptions accurately. Targets remain usable with browser zoom, large text and device scaling. Pen input is text/selection input unless a separate extension explicitly implements ink; pressure/tilt samples are not document text. Handwriting/Scribble and voice input use normal qualified replacement/composition paths.

## Mobile typing and keyboard controls

Virtual keyboards may omit keydown, report `Unidentified`, batch/delete/replace text and deliver noncancelable or missing beforeinput. Reuse the existing input/DOM fallback and composition ownership; do not translate every key into a second edit. Test prediction acceptance, autocorrection, double-space punctuation, swipe typing, emoji panels, dictated corrections, handwriting, selection replacement, CJK/Indic/RTL input and mixed hardware/virtual keyboards. Preserve platform-produced characters rather than guessing or undoing autocorrection from key history. Automatic Markdown/slash triggers require the conservative eligibility contract; ambiguous replacement input remains literal and explicit commands stay available.

`inputmode`, `enterkeyhint`, `autocapitalize`, `spellcheck`, `lang`, `dir` and supported `autocorrect` controls are hints with browser-specific results. Use a host-declared prose/code/command-search profile. Keep rich prose multiline; an Enter label of Done/Go/Send does not itself authorize form submission or change Enter semantics. Code remains literal; hints may suppress correction where supported, but the engine must preserve the text actually committed by the platform. Changing hints must not remount the editable root, interrupt composition or forcibly reopen the keyboard. Avoid numeric-only keyboards that make ordinary document characters unreachable.

Mobile users may have no Shift, Escape, Tab, modifier keys or visible undo. Expose reachable soft break, undo/redo, formatting, list/code indent/outdent, link, plain-text paste and command discovery actions. A supported command is not accessible solely through a desktop shortcut, slash keystroke or hover. Hardware keyboards retain the platform bindings in the interaction contract; connecting one must not leave an obsolete keyboard inset or select a different document model.

Capture semantic selection before a toolbar action; internal control focus/pointer transitions preserve the intended range. Restore focus only for a current user action whose editor/session is still active. Do not steal focus back after the user navigates elsewhere. Async completion cannot force a keyboard to reappear. Menu/dialog controls may intentionally own focus and require their own native keyboard; distinguish these from formatting buttons that preserve the editor selection. Programmatic focus or keyboard show is a request, not proof that a browser displayed the keyboard; respect user-activation restrictions and recover when it declines.

The browser adapter exposes opt-in `commandControls: true` and `editor.commandControls`, replacing the standalone plain-paste helper with labeled 44 CSS px command buttons, an explicit search input and native-paste fallback guidance. Controls capture existing single-use commands before pointer/Tab focus transfer. Search owns only its control subtree; another editor or host control permanently invalidates that intent. Literal clipboard reads begin only at explicit activation, revalidate the captured revision/permissions/anchors and never request focus after asynchronous completion. Disposal cancels retained targets and removes controls/listeners; ordinary native input remains the default when controls are disabled. Hosts may use `setInputHints({profile: 'prose' | 'code' | 'search', enterKeyHint?, lang?, dir?})`; changes wait through composition, retain the root and do not infer keyboard visibility. Declined focus leaves manual tap guidance without retrying or changing Enter/form policy.

## Viewport, scrolling and keyboard occlusion

Start with the browser's ordinary scrolling/keyboard behavior. Use CSS layout and a `VisualViewport` adapter when available to keep the active caret and essential controls inside the visible region; use window/scroll-container resize/scroll fallbacks otherwise. Do not infer keyboard presence solely from `innerHeight` changes: browser chrome, zoom, rotation, split-screen and floating keyboards also change geometry. Coordinate viewport offsets/scale, root bounds and scroll-container coordinates explicitly; never blindly divide every pointer coordinate by device pixel ratio or viewport scale.

Qualify dynamic/small/large viewport units and safe-area insets for the host layout. Avoid fixed `100vh` assumptions, double safe-area compensation and toolbars behind the home indicator. `interactive-widget` is a host document viewport policy; the SDK reports requirements and accepts a declared mode rather than rewriting the page's meta viewport. Record both requested and observed viewport modes: unsupported or ineffective metadata remains a request, and compensation follows observed geometry rather than a presumed support boolean. New browser implementations and release versions need direct verification; neither an umbrella bug status nor a landed patch establishes stable support.

With native resize behavior, follow the visual/layout viewport actually delivered. Keyboard-overlay mode is opt-in and must supply correct occlusion handling; do not compensate twice if both browser resizing and VirtualKeyboard geometry are active. Floating/split keyboards may not be represented by a full-width bottom inset. Keep a scroll/focus/manual reposition fallback when exact occlusion data is unavailable, and record residual limitations. Toolbars and suggestion panels reposition or become reachable sheets when space is too small; do not obscure the caret or trap the user's only dismissal/format action.

All overlays consume one coordinate convention and bounded scheduled measurements. Coalesce viewport/scroll/resize notifications into at most one geometry-read batch and one write phase per active window per animation frame; stop when no dirty visible surface needs work. Register scroll sources for the actual host root, including nested containers and same-origin iframe ownership. Do not probe or control a cross-origin parent's viewport. Repositioning must not emit selection/content changes, continuously call scrollIntoView or fight browser scroll anchoring. Follow the caret after a local edit/focus request; remote edits and passive layout changes must not drag a reader to another block.

## Browser capability policy

| API or feature | Default and fallback |
|---|---|
| Selection, Pointer Events, beforeinput/input/composition | Required adapter behavior with qualified event fallbacks; actual OS selection/IME evidence remains mandatory |
| VisualViewport, viewport units and safe-area CSS | Progressive positioning/layout; preserve ordinary scroll and usable static controls if absent or incomplete |
| VirtualKeyboard and keyboard inset variables | Optional geometry/host keyboard policy; feature-detect, check applicable context, handle errors and restore document-global overlay policy through a host-owned lease. No automatic show/hide on every render |
| Keyboard `getLayoutMap` | Optional shortcut-label aid; handle absence, rejection and layout changes. Labels do not redefine semantic keys or override AltGraph/IME |
| Keyboard lock | Disabled for ordinary editing. An explicit host fullscreen/kiosk capability may request it only in a supported context, with an accessible escape and release on cancel, focus loss or teardown |
| EditContext | Experimental alternative input adapter only after a separate measured feasibility decision. Retain the contenteditable fallback; do not add it to the default bundle or assume it provides rich rendering, selection UI, clipboard or accessibility |
| Clipboard, file input, File System Access, Web Share | Prefer user-initiated capabilities; handle unavailable/denied/canceled/unsupported MIME paths. Native paste, file input and explicit copy/download fallbacks remain available |
| Screen orientation/fullscreen/window segments | Optional host features, never required for editing; rotation/reflow works without orientation lock or segmented-window APIs |

Feature presence is not successful authorization or correct behavior. Guard secure-context, user-activation, permissions-policy and embedding constraints per API; never prompt on mount or repeatedly after refusal. Metadata and browser support tables are planning inputs; record actual tested versions/capabilities at release. A host owns page-global policy across multiple editors; destroying one editor cannot reset another's active lease or the host's settings. No new service, microphone provider or paid API is introduced.

## Clipboard, browser lifecycle and recovery

Preserve the existing import precedence, literal mode, whitespace and safe parsing contracts. Cover long-press Copy/Cut/Paste, native share/paste sheets, image/file clipboard items, delayed permissions and cross-application rich text. Read each chosen payload once, bound preparation, and capture session/anchors before asynchronous work. Cancellation or failed cut retains the original text. If scripted clipboard reads are unavailable, expose native paste guidance and normal editing rather than an unusable disabled editor.

File pickers/camera capture/share sheets may suspend or blur the page. Treat their results as asynchronous user actions with stable targets; cancellation is harmless. The `capture` attribute is a hint, not guaranteed camera availability. Backgrounding, pagehide/pageshow, BFCache restoration, process eviction and connectivity loss need explicit recovery checks: suspend disposable observers/gesture state, validate the recovered session before accepting callbacks, restore durable state through existing storage, and prevent duplicate listeners. Best-effort flush is not an unload durability guarantee. Existing localCommitted/remoteCommitted semantics remain unchanged. Keep credentials, document text and clipboard payloads out of routine diagnostics.

## Extension conformance

Baseline modules expose touch-usable actions even with enhanced mobile presenters disabled. Rich extensions reuse the shared focus/viewport/capability ports and [extension case catalog](../tests/mobile-extension-cases.md): menus and references need a visible invocation path and bounded anchored results; tables/code need touch command access and scroll/selection coexistence; reorder/resize need cancellation and tap alternatives; assets/embeds need native picker/permission/recovery behavior; converters need import/export fallback and loss diagnostics; assistive presenters retain baseline OS input with the extension off.

A presenter declares pointer/focus/scroll ownership, loading trigger, per-instance resources, capability fallback, cancel/dispose behavior and tested web-device envelope. Registration does not start listeners, decoders, uploads, workers or geometry loops. Native SDK conformance remains in its existing tracks; a mobile browser pass cannot substitute for it.

## Overhead and evidence gates

Use the [gzip bundle budgets](verification.md#browser-bundle-size-budgets): 512 KiB total / 32 KiB editor JS hard caps and 256 KB total / 16 KB editor JS preferred sizes, with hard caps in KiB = 1,024 bytes and preferred sizes in KB = 1,000 bytes. Retain existing initialization and input latency targets. Proposed incremental baseline allowance for this work: at most **5 KB gzip JS** over a feature-equivalent packed baseline, inside the 32 KiB total JS cap rather than added to it. MWB-1.1 records the baseline artifact/profile and confirms or explicitly revises this planning allocation before implementation measurements; an overrun requires a recorded decomposition/budget decision, not silent acceptance or removal of essential access. Revising the incremental allocation cannot waive either total hard cap.

Baseline admission also requires no new default third-party runtime dependency, worker, network request, polling timer or perpetual animation frame. Measurements/listeners scale with mounted/visible consumers, not document length; no full-document scans on key, pointermove or viewport events. For optional modules, absent/disabled means zero optional import/evaluation, assets, network, active listeners/observers and frame callbacks; enabled-idle means no continuous polling. Share only actual duplicate work and lazy-load expensive gesture, media, conversion or experimental API code.

Measure baseline/enabled/disabled packed consumers with identical documents and device profiles: raw and compressed bytes, cold parse/evaluation/startup, first usable edit, input-to-frame p50/p95/p99, geometry/layout counters, scroll/drag long tasks, memory after repeated mount/keyboard/rotate cycles, and resource counts after disposal. Existing phone input-to-frame and menu targets remain provisional until qualified; emulated timing may satisfy the virtual profile budget gate but must be labeled as emulator performance, not physical-phone performance. New support must meet the reviewed total limits and its incremental allowance; publish feature costs and retained failures.

Automated mechanics cover capability absence/rejection, event ordering, viewport transitions, pointer cancellation and semantic invariants. Physical or named iOS/iPadOS Simulator and Android Emulator browser runs cover keyboard, native handles/context menus, zoom, focus activation and browser chrome; use tested virtual equivalents for unavailable hardware-only/screen-reader observations. Record browser engine and mode (tab, installed web app or embedded host) explicitly; a Chromium-emulated iPhone is not Safari, and desktop WebKit is not iOS qualification. Reuse prior exact-revision cases where valid, but every new claimed combination needs evidence. Unsupported APIs may pass fallback cases; required editing capabilities cannot be marked unsupported merely to close the roadmap.
