# Verification and supported envelope

## Evidence contract

Every task adds or identifies its named deterministic check before running it. Planned test files/scripts in task contracts do not exist until implemented; a missing check is a failure, not permission to skip. Record exact command, revision, fixture seed/hash, executed/passed/failed/skipped counts and artifact path in progress. Rust name filters must execute at least one intended test. No paid inference or external model transport belongs in any check.

Use built-in Rust tests initially, Node's deterministic test runner for compiled JS adapters, and pinned Playwright for automated browser mechanics. OS IME, accessibility, native keyboards, autocorrection and dictation need a separately recorded physical or virtual platform matrix under the policy below. Synthetic key events and Playwright WebKit do not establish full Safari or real-device input support.

## Platform qualification with simulators, emulators and VMs

User decision, 2026-10-14: "Full platform will not be available only on emulators so that will have to do. Modify roadmaps accordingly to accept emulators". Named target-platform simulators/emulators and desktop OS VMs/test hosts are accepted for all platform and release qualification gates. This amendment changes platform/device evidence only; deployed-service evidence, independent security review and publication authorization remain separate requirements. Physical hardware is optional; retain physical observations such as the HONOR Pad X8a results where available. This supersedes the earlier development-only emulator exception and physical-only/manual-only clauses across roadmaps and case catalogs.

Use iOS/iPadOS Simulator with the platform Safari/native controls, Android Emulator with Android Chrome/native controls, and macOS/Windows/Linux native OS hosts or VMs with the claimed browser/toolkit and desktop session. Record runtime/image, guest and host OS, virtual device, browser/toolkit, keyboard/IME/locale/accessibility, input method, app mode and implementation/package/fixture hashes. A Chromium mobile viewport is not iOS Safari, desktop Playwright WebKit is not iOS Simulator, and mock callbacks alone are not target-OS execution. Native SDK gates still require native controls and the packaged native engine, not a WebView/browser replacement.

Required implemented behavior and semantic/selection/history/storage invariants must pass in the accepted runtime. Use its OS input, menus, clipboard and accessibility APIs where available. For observations unavailable only because of virtual hardware (microphone/dictation quality, physical keyboard/stylus/gesture behavior, vendor-only input services or manual screen-reader exploration), the owner records the unavailable capability, links an actually executed deterministic native/platform-boundary or accessibility-tree/action equivalent, verifies any advertised fallback and declares the remaining physical observation deferred. These virtual equivalents satisfy the corresponding qualification gate; physical/manual availability is not a blocker. They do not prove physical recognition quality or hardware behavior. Missing editor implementation, failed required behavior, nonexistent checks and untested platform-boundary/fallback behavior remain blockers.

Receipts distinguish `physical-device`, `simulator`, `emulator`, `vm` and `os-host` execution and identify each case's direct runtime observation or tested virtual equivalent. Record executed/passed/failed/skipped counts for the checks actually run and list deferred physical observations separately; never count a missing physical run as executed or passed. Preserve historical failed/BLOCKED receipts and raw HONOR results unchanged. A policy amendment, package build or small preparation probe does not itself close a task or qualify the complete SDK.

Apply existing correctness, security, package, bundle-size and measured performance gates to the declared virtual/physical profile. Compare baseline/candidate on the same runtime, host resources, fixtures and artifact features; retain raw timing/resource samples. Virtual measurements may satisfy release budgets and the full platform milestone, but publish them as simulator/emulator/VM results rather than physical-phone performance or universal hardware parity. All tests still use prepared deterministic data and mocked provider transports; no paid inference, credential loading, fixture recording or publication is authorized by this amendment.

FMT-1.15-V1, INT-1.14, MWB-1.11, MWX-1.8, REL-1.6 and DEL-1.7/1.9/1.10 may complete on the accepted virtual matrix. Their required case/profile coverage and current-artifact evidence remain mandatory. FMT-1.15-V2's original five-case single-platform development receipt remains a subset, not automatic completion of V1 or the release matrix. ## Browser bundle size budgets

The default Task preset has two independent gzip release caps. Preferred sizes are optimization goals; exceeding either hard cap blocks release qualification. Hard caps use KiB (1,024 bytes); preferred sizes continue to use decimal KB (1,000 bytes). The user approved these binary hard caps on 2026-10-13: 512 KiB total (524,288 bytes) and 32 KiB editor JavaScript (32,768 bytes).

| Scope | Hard cap | Preferred size |
|---|---:|---:|
| Task preset total JS + WASM + essential CSS/assets, including Yrs; optional Markdown excluded | 512 KiB (524,288 bytes) | 256 KB (256,000 bytes) |
| Editor JavaScript, including generated WASM glue and required runtime dependencies | 32 KiB (32,768 bytes) | 16 KB (16,000 bytes) |

Measure production artifacts with gzip level 9 and fixed metadata, summing each distinct delivered resource once. Include required code even when loaded lazily, and preserve the declared schema, rich-text editing, collaboration, persistence and supported default clipboard/link capabilities. Count generated WASM glue in both the JS subtotal and total. Exclude document data, development/test code and unrelated host application code. Record minifier/compressor versions/settings, artifact hashes, raw/gzip/Brotli sizes, both budget results and preferred-size results. Brotli is diagnostic and cannot substitute for gzip admission.

Disabled optional feature assets may be excluded only when production import/request evidence proves absence. Report enabled optional configurations and their additional costs separately; do not use a disabled/minimal configuration to claim that a larger default profile meets these caps. Mobile baseline additions remain inside both caps. Missing required artifacts or measurements fail admission; a hard-cap overrun cannot be accepted as a provisional performance result or silently waived. Changes to either cap require an explicit user-approved budget decision.

The user-approved 2026-10-13 profile change excludes Markdown parser/codec assets from the default Task admission only when static import graphs and runtime network/instantiation evidence prove their absence. Markdown is an explicit optional extension, not required lazy code in the default profile. Measure the enabled extension assets, incremental transfer and combined editor-plus-extension totals separately and qualify its complete Markdown behavior; do not present these enabled totals as passing the default caps unless they also pass. The optional-Markdown profile decision does not itself change the size budgets; the later user-approved binary hard-cap revision above applies, and preferred sizes remain unchanged. Other required features cannot be excluded by this decision.

SDK-1.8 implements the default Task artifact reductions, reproducible inventory and executable cap assertions before REL-1.2 establishes feature-equivalent comparison baselines. REL-1.2/1.3, EXT-1.9 and FIT-1.6 consume the same budget contract and harness. Preferred-size misses remain visible optimization work even when both hard caps pass.

The existing SDK and architecture-fitness roadmaps' [extension DX and size work](extension-dx.md#size-reduction-and-compression), especially FIT-1.10, SDK-1.13, reuses this harness and these unchanged caps. Generic public preset naming cannot reclassify existing required Task bytes or erase legacy evidence. Measure facade overhead, each optional extension, dedicated initial/deferred assets and combinations, with exact raw/gzip/Brotli inventories and local HTTP compression/cache provenance. Attribute before optimizing, preserve Unicode and feature-equivalent behavior, and report actual savings/tradeoffs rather than promise a percentage. Compression transfer savings do not establish smaller decompressed memory or faster WASM compilation.

## Multi-editor and cross-route resource accounting

The [SHR-01–SHR-08 cases](web.md#required-shared-resource-cases) add resource-reuse evidence to the existing single-profile budgets. Keep the default Task caps above unchanged and independently enforced; a mixed page containing optional features is a separately reported union. Report each profile's standalone inventory, the page/site union of unique required resources, incremental resources for the second editor/route, and actual network body transfers. Count an artifact referenced through one shared URL once in that union; identical bytes emitted or delivered under different URLs are duplicate delivery candidates, not a deduplication win. Required lazy assets still count. Do not divide bytes by editor count to pass a cap or hide duplicates behind a warm cache.

Use a pinned installed-tarball production site with recorded build graph/hashes and controlled local HTTP cache headers. Separate cold/cache-disabled, same-realm remount/client navigation and warm-cache full-navigation runs. Record server request/status/body-byte logs, browser cache provenance, JS evaluation/WASM initialization counters, live/disposed handles, first-visible/first-edit samples and per-instance retained resources; a 304/cache hit is not a fresh body download, and each new realm may compile/initialize again. SDK-1.9/1.10 create the receipt; FIT-1.6 checks graph/sensitivity, REL-1.3 measures browser-release profiles, DEL-1.2 qualifies product isolation and DOC-1.37 teaches only qualified behavior. Counts, failures/skips, exact revisions and teardown remain mandatory. This planning amendment executes none of these runtime cases.

## Provisional performance targets

These are retained design targets from the proposal and have no measured result yet. Pin actual hardware, browser/OS versions, CPU/network profiles and capability parity before making comparisons.

| Metric (p95 unless stated) | Desktop | Mid-range phone |
|---|---:|---:|
| Core ordinary edit | 1 ms | 2 ms |
| Input to visible update, controlled 60 Hz | 16.7 ms | 33 ms |
| Warm task activation | 50 ms | 100 ms |
| Warm long actual editability | 200 ms | 400 ms |
| Warm large actual editability | 750 ms | 1,500 ms |
| Matching preview first viewport | 50 ms | 100 ms |
| 10 KiB Markdown paste to formatted frame | 50 ms | 100 ms |
| 100 KiB Markdown paste to formatted frame | 150 ms | 300 ms |
| Local slash menu after ready | one frame | two frames |

Measure transfer, decode, compilation, instantiation, CRDT restore, DOM adoption, first accepted edit, p50/p95/p99, long tasks, memory plateau, peak paste memory, journal amplification and remote bursts. Warm includes local persistence restore; cold includes uncached assets and document transfer. Emit raw samples; summaries alone cannot establish a regression.

Qualify Task and Long as initial supported sizes. Large and Aged remain diagnostic stress fixtures until qualified. Missing a provisional latency/resource target requires a recorded release scope/architecture decision and honest published envelope; this does not waive the hard gzip bundle caps above. Data loss, silent import loss, divergent states, broken supported IME, corrupt undo, unsafe paste and stale-target overwrite cannot be waived as performance tradeoffs.

## Extension dispatch and JS/WASM performance

The [extension boundary contract](extension-dx.md#core-and-extension-boundaries) is qualified through existing SDK-1.11/1.12/1.13 and FIT-1.10/1.11; EXT-1.14/1.15 own interface admission. Extend the existing feature/profile, packed-consumer, browser input and byte-inventory producers. Create the named `extension-dx` performance group before invoking it; unknown groups, zero matching cases and missing required artifacts fail. This is additional planned acceptance, not a completed benchmark or new roadmap.

| Comparison | Required evidence |
|---|---|
| Direct existing ports vs facade, identical features | Local command/commit and input-to-visible p50/p95/p99; dispatch time, candidate visits/callbacks, JS/WASM calls, copied/encoded bytes and allocation counts. Separate host callback cost from SDK overhead. |
| Empty, disabled, one enabled and 10/100 unrelated extension descriptors | Same changed-range operation with increasing document sizes. Disabled/uninterested callbacks and collaboration-owned work stay zero; input dispatch does not walk the whole registry/document. Include scoped matching, selection-only and structural/format changes with no text delta. |
| Local comment, formatted editor, collaborative document on one page | Independent options/history/identity/authority, shared compatible immutable code, no local-field collaboration work, local input under deterministic remote bursts, attach/detach races and repeated disposal. Report presence enabled/disabled separately. |
| Pure JS vs WASM candidate where semantics permit | Equivalent inputs/outputs, tiny/medium/large payloads, single/batched calls, cold/warm runs; separate JS glue, UTF-16/UTF-8 conversion, copying, kernel, result decoding, compile/instantiate time and memory. Report crossover or no safe gain, not just fastest large batch. |
| Representative user work | Short-field typing, selection/formatting, IME commit, 10/100 KiB paste, Task/Long editing, risk-selected heavy combinations, cold first edit, warm activation, remote bursts and memory after repeated mount/disposal. Large/Aged remain diagnostic until qualified. |

Before candidate measurements, pin identical semantic/capability inventories, direct-port baseline, workload sizes, extension counts, browser/OS/device or virtual-runtime identity, build/package hashes, compiler flags, cache state, warm-up, sample count and aggregation method. Interleave baseline/candidate runs; retain raw samples and dispersion. Pin absolute latency limits from the existing provisional targets and a numerical maximum allowed regression for each supported workload in the feature profile before seeing candidate results. Do not derive tolerance from a slower candidate or average away a regressed typing/selection case with a paste/export win. Timer-resolution/noise limits produce an inconclusive result and a bounded remeasurement hypothesis, never a zero-overhead claim.

Work-count assertions are deterministic regression gates even when timing is inconclusive. Include deliberately corrupted controls that eagerly load collaboration, notify an unrelated listener, scan every descriptor, serialize the full document on input, or add per-character boundary calls; the corresponding oracle must fail. Runtime measurements run the real compiled engine and input/lifecycle path with prepared/mock transports. Microbenchmarks attribute cost; they cannot replace end-to-end correctness or platform input checks. Record nonzero executed/passed/failed/skipped counts per comparison and retain failed/rejected experiments. Existing byte caps and correctness gates remain unchanged; unmet provisional latency targets use the existing release-scope decision policy above and do not become a passing speed claim.

The deeper [research](../evidence/editing-performance-extension-research.md) extends existing performance gates without claiming measured improvements. Compare baseline versus presets separately as explicit feature-cost experiments, with all other variables controlled. Report raw samples, sample count, median/p95/p99 where statistically meaningful, outliers and failures. An unrepresentative sample set is inconclusive rather than a tail-latency pass.

Measure input arrival through visible text/caret presentation separately from Rust command, FFI, patch/render/layout, persistence queue and optional-service costs. Web INP supplements these measurements but excludes continuous drag/scroll and cannot qualify them. Include long paragraphs/code lines, large selected ranges, tables, images, bidi/Unicode, active composition, slow optional work, collaboration bursts and multiple editors. Run baseline with no extensions, shipped presets and high-risk mixed features; optional work must not multiply baseline keystroke costs with total document size. Record changed blocks/bytes, rendered nodes, geometry reads/writes, queue bounds, cancellation and cache invalidation against actual edited regions. Asymptotic claims require several document sizes and raw traces, not one fast fixture.

Exercise sustained selection autoscroll and text dragging at the device's refresh rate, keyboard-open mobile viewports, native candidate windows and accessibility clients. Record missed-frame/long-task traces and the declared per-device thresholds; do not invent a universal frame guarantee or infer smoothness from average FPS. Idle editors must not poll continuously; coalesce adapter geometry per frame and stop scheduling when no interaction is active. Search/highlighting/conversion results are revisioned/cancelable and never restart a whole-document scan on every selection movement. Repeated mount/dispose, canceled transfers and extension unload must release resources and show a bounded memory plateau under a fixed replay. Tests use deterministic data/transports only. Performance evidence cannot waive content, selection, accessibility or history correctness.
