# Exact change and revision views

Feature implementation keeps focused deterministic correctness/data-safety checks; device rows and D observations run later on accepted simulators/emulators/VMs/OS hosts without waiting for physical hardware. Preserve original case IDs and criteria; deferred observations remain unchecked and do not block web feature completeness. Exhaustive qualification/performance follows the stated later phase.

Status: planned, roadmap 13. “Exact” identifies what is compared; it does not claim a unique diff algorithm or byte-preserving rich-text serialization.

## Three representations

1. **Source diff:** immutable original and edited UTF-8 bytes for a file/source session, including newline style, final newline and source spelling. Retain both hashes and explicit decode limits. Binary/invalid UTF-8 input returns a diagnostic.
2. **Projected Markdown diff:** deterministic serialized before/after rich documents, tagged with serializer/dialect versions. Show that serialization may normalize author spelling. Never label this the original source diff.
3. **Semantic diff:** stable node IDs, insertion/deletion/move, attributed text, marks, attributes and unknown/opaque content changes. Formatting, link targets and table structure remain visible even where Markdown cannot represent them.

CRDT binary update exchange is a fourth, internal transport representation; it is never substituted for these review views. Review can align text and semantic changes, but if alignment is ambiguous it must show separate views rather than fabricate correspondence.

## Immutable revisions and retention

Revision requests bind document/epoch/schema/module profile, observed-state token, representation type and hash. Store snapshots or reconstructable immutable history in a separate bounded HistoryStore. Capture named revisions/checkpoints on demand and materialize incremental history outside the typing path; do not serialize the entire document every keystroke.

A locally monotonic generation may label revisions but must be persisted and scoped; it is not a cross-replica total order. Deletion effects participate in exact revision validation. Availability after pruning, encryption key rotation or schema migration is explicit. Return unavailable/locked/incompatible for a missing revision, never approximate it from the current document. Yrs GC and UndoManager are not an archival history API.

### Named snapshot store (DIF-1.2)

The session companion exposes an in-memory, host-owned snapshot store, separate from the live replica and durable session journal. A host supplies a bounded store namespace; opaque handles contain that namespace, a process-local store instance and a local capture sequence, which is not a persisted revision or global order. Every read binds the complete captured scope, representation and hash. Missing handles return missing; previously issued evicted handles return pruned without retaining unbounded tombstones. Schema/module mismatch returns incompatible; other mismatched request bindings reject explicitly.

Count and encoded-byte retention are FIFO. Byte accounting includes retained label/profile/scope metadata as well as payload. Oversized captures reject before eviction; reads borrow immutable data, so the store owns no unbounded materialization cache. Capture is an explicit operation with a current observed revision check and a read-only engine callback. No capture hook is installed in edit/undo/receive paths. The callback owns representation provenance; engine projection adapters are delivered by DIF-1.4.

An optional host key-profile label records the access generation needed to read a snapshot. Missing or rotated key access returns key-unavailable. This decrypted in-memory store is not an encryption boundary; hosts must enforce authorization and optional encrypted persistence before supplying access. Source text is omitted from store diagnostics. Capture labels are user-supplied, not authenticated attribution. Named snapshots and their capabilities disappear with the host-owned store; durable archival storage and restoration are not claimed here.

### Semantic comparison model (DIF-1.4)

The on-demand diff companion copies the engine's read-only projection, including visible/recovery nodes, integrated source spans, attributed runs, original block tuples, editor metadata and complete retained structure. It never substitutes presentation fallbacks for unknown tuples. JSON-incompatible engine values reject explicitly; node/byte/depth limits apply before capture. No observer or typing hook is installed.

Version `editac-semantic-diff-v1` compares compatible immutable semantic revisions by stable node ID. Insert/delete, visibility, placement, kind, text, formatting, references, table, attributes, opaque modules and source identities are independent facets; a move never suppresses another facet. Run segmentation is normalized only for comparison of UTF-16 mark ranges. Link values have a separate reference facet; built-in reference/table tuple changes additionally have their own facets. Unknown tuples and marks stay inert and visible, with full before/after node payloads. Retained structure changes remain an explicit document-level before/after result even without visible changes. Ordered IDs and facets are deterministic, output bytes/change count are bounded, hashes and revision scopes bind inputs, and attribution is always unknown. This model does not apply edits, infer authors or establish Git/browser/native presenter qualification.

## Patch contract

Pin deterministic line/word diff algorithms and options. A patch carries before/after hashes, representation/profile, limits and hunk ranges. Applying it to the exact baseline must yield byte-for-byte expected output and the expected hash. Wrong baseline, overlapping hunks, malformed lengths, missing context or output-limit violations fail without mutation. Git-like unified output is an interoperability format, not a promise that tie-breaking matches every Git version/options combination.

Use fixed `git diff --no-index` golden cases to validate conventional unified output; exit 1 means differences. Test repeated lines, CRLF/LF, missing final newline, Unicode/emoji/combining text, large replacements and moves. Text offsets exposed to the editor convert through UTF-16/anchor validation; terminal columns and UTF-8 bytes are distinct units.

Applying a reviewed hunk to a live collaborative document uses source reconciliation or stable semantic commands and current revision checks. It never patches serialized Markdown and re-imports the whole live document. “Accept all” means apply the validated proposal. Partial hunk application recomputes a valid semantic plan and rejects unsafe fragments (for example half a fenced block).

### Session review admission (DIF-1.5)

The source review adapter captures an opaque source baseline, ordered owner bindings, source mode and full observed revision. A proposal carries an exact patch; “accept all” validates its full baseline/output hashes and bounds before preparing semantic reconciliation. Partial acceptance uses strictly increasing zero-based hunk indexes against original line positions, validates the full patch first, then recomputes a complete selected source candidate and a fresh reconciliation plan. Empty selection is a no-op. Host and recorded patch limits both bound selected output; the endpoint also budgets base plus candidate bytes. The underlying reconciler's supported mappings remain authoritative: ambiguous structural changes reject rather than replacing live identities.

Whole-document Markdown grammar events distinguish fenced from indented code, including quote/list nesting. Review requires an explicit fenced-block close; a permissive EOF close or a literal fence-like final content line cannot make a partial fragment safe. Literal source mode does not apply Markdown syntax rules.

Preparation and application both bind the integrated observed revision, including deletions. Prepared review edits are opaque and consumed on application, which delegates to the existing service's current writable/history/module/permission/limit checks, semantic undo grouping, journaling and trusted-host origin admission. Client routing tags remain untrusted attribution. No live document reimport or automatic historical capture is added.

Rejected valid candidates retain exact base, selected proposed and full-proposal inputs plus the current semantic projection. Malformed patches or invalid selections explicitly lack a materialized selected candidate; projection failure is explicit rather than fabricating current source. Default review diagnostics expose only reason categories and input lengths. Store acknowledgment failure follows the existing unsaved/recovery-required policy and reports the actual post-mutation current state; it is not represented as an atomic semantic rejection.

## Portable presenter export (DIF-1.8)

`editac-change-model-v1` is a bounded JSON envelope `{version,input}` for companion terminal/native/web presenters. Input is exact-source unified wire, projected-Markdown wire with nonempty serializer/dialect, or the complete `editac-semantic-diff-v1` model. Preserve hashes, newline metadata and independent semantic facets; projected input retains normalization warnings. This is presentation data, not an edit capability, authenticated attribution, or a global causal history. Semantic attribution must be `unknown`; text exports carry no author field. Consumers reject unsupported versions/representations, malformed payloads and byte-limit excess before displaying them. Terminal columns, UTF-16 editor offsets and UTF-8 source bytes remain distinct.

The Git qualification profile pins Git 2.53.0, Myers, three context lines, no indentation heuristic, no color, no external diff/text conversion and no user/system configuration. With no error diagnostics, exit 0 is equal and exit 1 is different; other codes or error diagnostics reject (missing paths can also return 1). Fixed unambiguous goldens compare conventional output, while repeated-line/move cases prove exact hash round-trip and Git application without promising identical tie-breaking. Large-diff receipts report fixture bytes, comparison/output limits, actual durations and rejection results; these prepared desktop measurements do not qualify release/device performance targets.

## Views and attribution

Provide accessible unified, inline and side-by-side web views; a portable changes model feeds native and terminal presenters. Readonly current, readonly historical and writable live modes are distinct. History checkout cannot rewind the live replica. “Restore this version” produces a new authorized edit against the current state with a preview and conflict result.

### Optional web historical review (DIF-1.7)

The host-owned `WebHistoryStore` captures detached engine semantic projections explicitly; no typing observer, binary checkout or durable archive is installed. The versioned projection, complete identity/module profile, local generation, provenance and key-profile metadata are SHA-256 bound. FIFO count and UTF-8 encoded-byte limits include metadata. Pruned/missing, incompatible scope and unavailable key access remain explicit. This decrypted memory companion does not authorize access or encrypt data; the host owns those policies and authenticated attribution evidence.

The supported browser comparison boundary captures a Rust-owned `editac-browser-semantic-capture-v1` payload at the same synchronous read boundary as the historical projection. It binds the complete engine identity, module profile, actual observed revision token and canonical semantic hash. Canonical semantic bytes travel as a UTF-8 string payload so JavaScript cannot change Rust number spellings during JSON round-tripping. `EngineHandle.captureSemantic(moduleProfile)` returns the detached projection and comparison payload; `compareSemantic(before, after)` delegates to the existing Rust semantic companion. `WebHistoryStore.compare(engine, beforeHandle, afterHandle, access)` resolves both captures under ordinary scope/key access and returns the complete semantic model. No supplied diff model, JavaScript diff, restore permission or live mutation is involved. Capture provenance remains host metadata; comparison attribution stays unknown.

BCC-1.1 acceptance refines DIF-1.4/DIF-1.7: same-scope real captures preserve every independent semantic facet, source identity and retained structure; missing/pruned/key-unavailable/incompatible inputs reject explicitly. A domain-separated SHA-256 binding additionally covers version, full identity, module profile, observed token, semantic hash and canonical payload. This is integrity framing, not host authentication. Rust revalidates that binding, payload version, complete identity/module scope, observed-token framing and canonical hash before comparison. Fixed browser limits are 1 MiB per encoded semantic revision, 10,000 nodes, depth 32, 10,001 changes and 4 MiB output; comparison request JSON is capped at 4 MiB before decoding. History limits still bound combined snapshot/metadata/payload retention. Rejections and comparisons preserve live snapshot, checkpoint/update bytes, generation, history, journal and subscriptions. Existing SDK consumers must compile; installed-package three-engine proof is separately required by BCC-1.2 before the owner return qualifies consumer implementation.

`HistoryReview` displays immutable projections with representation/unknown attribution labels and bounded pagination/value clipping. Historical inspection contains no mutation controls. A separate writable section previews restoration as a new edit. `HistoryRestorer` binds an opaque, single-use preview to the current semantic state and local observed generation, including deletion effects, and rechecks scope/key availability and writable policy synchronously before existing Rust semantic preparation/commit through the host storage lifecycle. Accepted edits keep existing node/source identities, produce ordinary local journal updates and an isolated undo group. A stale preview returns base/current/proposed recovery and a visible conflict; previewing again is explicit.

The public `EditorStorageOwner` exposes synchronous `commitPrepared(plan: PlanToken): CommitResult`, bound to its existing `LocalStorageLifecycle.commitPrepared`. `HistoryRestorer` hosts use `{ engine: owner.engine, commit: owner.commitPrepared, writable: () => hostWritable }`; request-based `owner.commit(request)` stays unchanged. The restorer rechecks the host's current writable/recovery permission, and storage rechecks live/closing/failure policy before engine admission. The bridge grants no new permission and does not bypass or add policy. Rust retains engine ownership, observed revision, single-use and released-token fencing. The caller owns `releasePlan` on success and rejection; `HistoryRestorer.apply` already releases in `finally`. Storage's existing update subscription journals accepted edits and flush remains the durability boundary. Disposing a view never disposes its borrowed owner; destroying the owner prevents further admission. BPA-1.1 qualifies this boundary with deterministic owner/history checks; installed offline three-engine proof and immutable main-union return remain BPA-1.2.

The initial engine adapter supports same-identity, same-structure unmarked text replacement. Unchanged marked/opaque nodes are retained. Changes to marks, opaque/block/editor attributes, placement, recovery or retained structure reject visibly as unsupported rather than normalizing, dropping data or reimporting the document. This conservative admission is a conflict result, not a claim of general structural/formatting restoration. Snapshot/hash/local generation do not prove a global causal order or per-character authorship; this semantic view never claims exact original source spelling. Host commit/storage failures retain the actual post-call current state in recovery; they are not claimed atomic after a host mutation.

Show authenticated operation attribution only when supplied by a trusted host, otherwise mark it unknown/unverified. Separate human/agent/import/replay origins and semantic undo groups. A reconstructed snapshot diff says what differs, not necessarily who typed each character; concurrent history cannot be turned into a single causal narrative without evidence.

No-loss criteria cover content, marks, URLs, unknown modules, whitespace and structural identity. Bounded review history, source files and recovery artifacts inherit optional encryption/access policies. Logs do not contain confidential source by default.
